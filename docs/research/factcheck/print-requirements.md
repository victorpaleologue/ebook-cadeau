# Fact-check report — print requirements

_Fact-check of `docs/research/03-print-requirements.md`, 2026-11-12. The corrections below were applied to that document in the same pass (status line: "fact-checked"). Implications added to the document after this pass are numbered 39–42._

## 0. Method and limits

- **Web search worked.** 11 fresh WebSearch queries (standard mode; the facts are stable specifications, except the profile licences), written from the claim, not from the document's wording. Vendor pages were not opened: where a verdict rests on the search tool's summary of a page, it says "per search summary".
- **Primary files read directly:**
  - Ubuntu archive packages (reachable from the sandbox): `icc-profiles` 2.1-2 (multiverse) and `icc-profiles-free` 2.0.1+dfsg-1.1 (main), downloaded with `apt-get download`, unpacked, and their `copyright` files, changelog, ICC headers and ECI information sheets (PDF) read.
  - The Scribus repository on `raw.githubusercontent.com`: `resources/profiles/ISOcoated_v2_300_bas.txt` (licence) and `ISOcoated_v2_300_bas.icc` (SHA-256 compared with the file bundled in `crates/ebc-card/assets/icc/`: identical).
- **Not checked**: Exaprint, Printoclock, Saxoprint, Helloprint, BoD, Bookvault and Lulu pages (no result or not searched); the ISO 15930 and ISO/IEC 18004 texts themselves; every claim of §6.1–6.2 and §7–8 (creasing, crease spacing, trims, catalogue products).
- Verdicts: CONFIRMED, PARTLY, WRONG, OUTDATED, UNSUPPORTED (no evidence found; not the same as false).

## 2. Omissions

1. **Licence of ECI profiles** forbids alteration and charging for distribution (row 10). Bundling them would add a non-permissive licence to a BSD-3 repository and to a web app that serves them; the project's choice of the zlib-licensed basICColor build (already in `ebc-card`) is the right one.
2. **FOGRA39L characterisation data under Zlib** (`icc-profiles-free`: `FOGRA39L.ti3`, also FOGRA28L–FOGRA40L): a permissive route to build our own FOGRA39 profile if ever needed (the profiling tool's licence then matters, not the data's).
3. **Onlineprinters' current label** is PDF/X-4:2010 (row 4).
4. **Flyeralarm accepts PDF/X-4** on products whose data sheet says so (row 6).
5. **Retail QR guidance has a maximum** (0.990 mm X-dimension at POS); irrelevant for a card, but the GS1 figures are not phone-camera figures.
6. **HP bottom margins** up to 17 mm (row 17).

## 3. What could not be checked

Exaprint, Printoclock, Saxoprint, Helloprint, BoD, Bookvault and Lulu figures; mark conventions (dashed fold ticks, "offset = bleed"); the ISO 15930 and ISO/IEC 18004 texts; creasing thresholds, crease spacing, trim sizes and catalogue products (§6–§8); the licence of the PSO v3 profiles.

## Code that should change if this correction stands

- `crates/ebc-card/assets/icc/README.md` and `crates/ebc-card/src/request.rs` (`bundled_fogra39`): no behaviour change; the provenance note can cite the verified Scribus licence and the matching hash. Add to the README that ECI's own profiles are under Heidelberg/ECI terms (no modification, no charge, licence must accompany) and must not be bundled; a printer that insists on the ECI file supplies it through `CardRequest::output_profile`.
- `crates/ebc-layout/src/profile.rs`: `HOME_PRINTABLE_MARGIN_MM` = 6.35 mm is not a safe bound for the trailing (bottom) edge of some inkjets; keep it for the long edges, and add a check (or a doc comment) that content stays ≥ 17 mm from the two **short** edges of the A4 sheet — already satisfied by the centred poche spread (33.5 mm free).
- Per-printer profiles (wherever they are stored, `ebc-layout` / `ebc-pdf`): Onlineprinters label "PDF/X-4:2010"; Flyeralarm accepts X-3:2002 or X-4 per data sheet; Pixartprinting's FOGRA39 and Exaprint's 300 % / PDF 1.3 marked unconfirmed.
- `crates/ebc-pdf`: keep always embedding `DestOutputProfile` (required for X-4). The degraded "registered condition, no profile" mode for X-1a/X-3 stays acceptable in practice.
- `crates/ebc-qr`: `QUIET_ZONE_MODULES` = 4, `MIN_PRINT_MODULE_MM` = 0.4 and `RECOMMENDED_PRINT_MODULE_MM` = 0.5 are consistent with GS1's POS minimum and target; doc comments can cite GS1 General Specifications §5.12.3.1 (via GS1 UK) instead of "memory".
- `crates/ebc-card` (`bundled-fogra39` is a default feature using `include_bytes!`): doc 03 implication 22 asks for the output profile to be loaded on demand, not linked into the WebAssembly binary (about 1 MB). Licence-wise the bundling is fine (zlib); size-wise, consider turning the feature off for the `ebc-wasm` build and fetching the profile when a professional output is requested.
